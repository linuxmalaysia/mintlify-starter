The deployment applies several security measures out of the box — every component runs on a hardened Wolfi base image, all Elasticsearch API traffic is encrypted with auto-generated TLS certificates, credentials are stored with restricted file permissions, and bind addresses default to localhost so nothing is exposed to the network without a deliberate configuration change. This page explains each layer and how to extend or verify it.

## Wolfi Hardened Images

All three stack components use Wolfi-based container images published by Elastic. Wolfi is a minimal, purpose-built Linux distribution designed to reduce the software supply-chain attack surface.

### Why Wolfi Images Are More Secure

- **Distroless base**: Wolfi images contain only the packages required to run the application. Shell utilities, package managers, and other OS tools are absent, which eliminates entire classes of container escape and privilege escalation techniques.
- **Minimal package footprint**: Fewer installed packages means fewer CVEs to track and patch. Each image's software bill of materials is small and auditable.
- **Reduced attack surface**: With no unnecessary binaries present in the container, an attacker who gains code execution inside the container has far fewer tools available to pivot or escalate.

## SSL/TLS Configuration

Elasticsearch starts with HTTPS enabled on port 9200. During first launch the container generates its own internal CA and issues a server certificate signed by that CA. The CA certificate is automatically copied out of the container and saved to `elk-wolfi/certs/http_ca.crt` on the host.

All API calls to Elasticsearch must present this CA certificate for server verification. Use the `--cacert` flag with `curl`:

```bash
curl --cacert elk-wolfi/certs/http_ca.crt \
  -u elastic:<password> \
  https://localhost:9200
```

<Accordion title="Trusting the CA system-wide">
  If you prefer to avoid passing `--cacert` on every request, install the CA certificate into your system trust store:

  ```bash
  # Ubuntu / Debian
  sudo cp elk-wolfi/certs/http_ca.crt /usr/local/share/ca-certificates/elastic-local.crt
  sudo update-ca-certificates

  # AlmaLinux / RHEL / Fedora
  sudo cp elk-wolfi/certs/http_ca.crt /etc/pki/ca-trust/source/anchors/elastic-local.crt
  sudo update-ca-trust
  ```

  After adding the CA to the system trust store, standard `curl` calls and most HTTP clients will trust the Elasticsearch certificate without any extra flags.
</Accordion>

## Credentials Management

The `elastic` superuser password is auto-generated when Elasticsearch first starts. The setup process resets it using `elasticsearch-reset-password`, captures the output, and writes it to `elk-wolfi/temp_credentials.txt` with `0600` permissions so only the owning user can read it.

Retrieve the password at any time with:

```bash
grep 'Elastic password' elk-wolfi/temp_credentials.txt
```

The same file also stores the Kibana enrollment token generated by `elasticsearch-create-enrollment-token`.

<Warning>
  Do not commit `temp_credentials.txt` to version control. The file is listed in `.gitignore`, but double-check that it has not been staged before running `git add`. Anyone with this file can authenticate to your Elasticsearch cluster as the `elastic` superuser.
</Warning>

## Image Signature Verification with Cosign

Elastic signs all official container images with [cosign](https://docs.sigstore.dev/cosign/overview/). Verifying the signature before running a container confirms that the image was produced by Elastic and has not been tampered with in transit.

This step is optional but strongly recommended for production and regulated environments. The `setup_elasticsearch.sh` script performs verification automatically when `cosign` is already installed on the host.

To verify manually:

```bash
# Download the Elastic public cosign key
wget https://artifacts.elastic.co/cosign.pub -O cosign.pub

# Verify the Elasticsearch Wolfi image
cosign verify --key cosign.pub \
  docker.elastic.co/elasticsearch/elasticsearch-wolfi:9.4.4

# Clean up the key after verification
rm cosign.pub
```

Run the same command for the Kibana and Fleet Server images, substituting the appropriate image reference.

<Tip>
  Install cosign via your distribution's package manager or from the official [Sigstore releases page](https://github.com/sigstore/cosign/releases) before running the setup scripts. When cosign is present, verification happens automatically as part of the Elasticsearch setup step.
</Tip>

## Bind Address Hardening

Controlling which network interface each service listens on is one of the most effective ways to limit exposure.

<Tabs>
  <Tab title="WSL2 / Local (default)">
    By default, all services bind to `127.0.0.1`. This means Elasticsearch, Kibana, and Fleet Server are only reachable from the same machine — they are invisible to other hosts on your network.

    No firewall rule changes are required in this mode. This is the safe default for development and testing.
  </Tab>
  <Tab title="Single Node / Multi Node">
    When `deployment_option` is set to `single_node` or `multi_node`, all bind addresses default to `0.0.0.0`, making the services reachable on every network interface.

    Update `group_vars/all.yml`:

    ```yaml
    deployment_option: "single_node"
    ```

    Or pass the override at runtime:

    ```bash
    ansible-playbook -i inventory/hosts.yml ansible/main.yml \
      -e "deployment_option=single_node"
    ```
  </Tab>
</Tabs>

<Warning>
  Setting `BIND_ADDRESS=0.0.0.0` (shell scripts) or `deployment_option=single_node` (Ansible) exposes all services on every network interface. Before applying this change, ensure your firewall permits only the required source addresses on ports 9200, 5601, and 8220. Leaving these ports open without restriction on a public network gives unauthenticated users access to your Elasticsearch cluster.
</Warning>

## Ansible Credential Handling

Sensitive values are handled carefully inside the Ansible playbooks to avoid leaking secrets into logs or terminal output.

<Steps>
  <Step title="no_log: true on sensitive tasks">
    Any Ansible task that processes a password, token, or enrollment credential is marked with `no_log: true`. This prevents Ansible from printing the task's arguments or registered output to the console, even in verbose mode.
  </Step>
  <Step title="Restricted file permissions on Compose files">
    Podman Compose files that embed service tokens or credentials are written to disk with `0600` permissions, ensuring only the owning user can read them. This applies to both the Elasticsearch and Fleet Server Compose definitions.
  </Step>
  <Step title="Runtime-only token injection">
    Fleet Server tokens (`fleet_server_service_token`, `fleet_server_policy_id`) are intentionally blank in `group_vars/all.yml`. Supply them at runtime with `-e` flags so they are never stored in the repository.
  </Step>
</Steps>
